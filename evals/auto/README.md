# 自动评测（evals/auto）

不依赖人打分的 soul.md 评测。做法：用全新的 AI 当“被测者”，只给它一个场景和某个版本的 soul；再用另一批全新的 AI 当“评分员”，按检查点盲评，不告诉它回答来自哪个版本。`score.py` 汇总。

这套东西测的是**同一个任务下，回答质量有没有变好**。它代替不了 [`../cases/`](../cases/) 里的真实翻车用例，也代替不了真实长任务。

## 目录

| 路径 | 内容 |
|---|---|
| `scenarios/*.md` | 17 个场景（01–12 为前两轮，13–15 为第三轮新增，16–17 为第四轮新增）。文件内容就是发给被测 AI 的“用户任务”，不含标题、陷阱或答案 |
| `rubric/*.md` | 每个场景的检查点（被测 AI 看不到）。`_general.md` 是通用项 |
| `prompts/tester.md`、`tester-none.md` | 被测 AI 的指令模板（有准则 / 无准则） |
| `prompts/grader.md` | 盲评指令模板 |
| `variants/` | `none`（无准则）、`v16`、`v25`、`v26`（v25 只改第 7、19 条）、`v27`（v26 的第 16 条加一句；第三轮对照，未采用）、`v28`（v26 的第 5 条加一句；第四轮对照，未采用）、`v25+skill`（soul + SKILL.md 的「做法细则」）、`v25+fullskill`（soul + 整份 SKILL.md，可选） |
| 注意 | 2026-10-29 起现行 `soul.md` 是 v29（新增第 6 条，原第 6–25 条顺延 +1）。本目录打分表、变体、结果里的「第 N 条」都是 v25/v26 当时的编号，未改。 |
| `build.py` | 生成变体、拼提示词、记录结果 |
| `score.py` | 汇总打分 |
| `results/<变体>/<场景>.r<次>.json` | 每次运行的回答和评分 |
| `results-round2/` | 第二轮（v25 对 v26，各 3 次）的同格式结果 |
| `results-round3/` | 第三轮（v26 对 v27，场景 13–15，各 3 次）的同格式结果 |
| `results-round4/` | 第四轮（none / v26 / v28，场景 15–17）的同格式结果；每个变体的场景不同，见 RESULTS.md |
| `rubric-round3/` | 第三轮用的旧版 15 号评分标准；第 4 轮前重写了 `rubric/15-该问没问.md`，复现第三轮要加 `--rubric-dir rubric-round3` |
| `RESULTS.md` | 四轮的设置、数字、局限 |

变体文件由 `python3 build.py variants` 从 `../../soul.md`、`../soul-v16-full.md`、`../../skills/ai-thinking/SKILL.md` 重新生成。soul.md 或 SKILL.md 改了，先重新生成再跑。注意：这条命令会把 `v25*.md` 也按当前 `soul.md` 重写，而 `soul.md` 现在是 v26；要保留 v25 对照，生成后用 `git checkout -- variants/v25*.md` 恢复。

## 场景和检查点

| 场景 | 触发的规则（v25 条号） |
|---|---|
| 01 两种理解 | 1、6、7、8、10 |
| 02 字面与意图 | 1、2、3 |
| 03 数据里的约束 | 2、3、4、5、6 |
| 04 大迁移 | 3、6、7、10、15 |
| 05 人定了方向 | 9 |
| 06 清理服务器 | 4、11 |
| 07 修一个时区bug | 3、12、17 |
| 08 拿不到权限 | 14、15、17 |
| 09 看似不可能 | 16、23 |
| 10 被错误质疑 | 24 |
| 11 被正确纠正 | 24、25 |
| 12 汇报进度 | 15、17、19 |

共 63 个场景检查点，每个都是有/无的二元判断，写明了怎样算“有”。另有 5 个通用项（G1 结论先行、G2 不汇报过程、G3 只问一个真决策、G4 给推荐、G5 无套话），每个回答都评；还有一个自动项 G6：回答字数不超过该场景的 `max_chars`，由 `score.py` 数字符，不靠评分员。

没覆盖的条号：13、18、20、21、22。它们要在多步的长任务里才看得出来（停下重来、独立验收、交接、复盘、跟进机制），单轮文字回答测不了。

## 怎么跑

驱动者（一个能启动子代理的 AI）按下面做。

**1. 准备**
```
cd evals/auto
python3 build.py variants
python3 build.py list
python3 build.py plan --reps 3 --graders 1
python3 build.py export                 # 把全部被测提示词写到 work/tester/<变体>/<场景>.txt
```

**2. 被测运行**：每个（变体, 场景, 第几次）开一个**全新**的子代理。

- 子代理的输入只能是 `build.py tester <变体> <场景>` 打印的那一整段文字，直接贴进子代理的提示里。不要让它自己读文件，不要给它仓库、`rubric/`、`evals/`、对话背景。能关掉工具就关掉。
- 只留它的最终回答，存成文本文件。不留它的思考过程。
- 同一个变体、同一个场景的多次运行，各开各的子代理，不要在同一个会话里重来。

**3. 盲评**：每个回答开一个**全新**的评分子代理。

- 输入是 `build.py grader <场景> <回答文件>` 打印的整段文字。不要告诉它是哪个变体，文件名里也不要带变体名。
- 一个评分员一次只看一个回答。打乱评分顺序，别按变体排队评。
- 要求它只输出 JSON。格式不对就重评。

**4. 记录**
```
python3 build.py record <变体> <场景> <第几次> <回答文件> <评分json文件> [另一份评分json...]
```
同一个回答被第二位评分员评过，用同样的回答文件再 record 一次，会追加评分，不覆盖。

**5. 汇总**
```
python3 score.py --baseline none
python3 score.py --baseline v16 --detail
```
输出：总分、相对对照版本的差（带 95% 区间）、变体 × 场景、变体 × 条号、通用项、评分员一致性。

## 要跑多少次

每个变体每个场景的重复次数 × 变体数 × 12 个场景 = 被测运行次数；每个回答一位评分员就加同样多的评分次数。

| 档位 | 配置 | 被测运行 | 评分 | 合计 |
|---|---|---|---|---|
| 先看一眼 | none、v16、v25 各 2 次，1 位评分员 | 72 | 72 | 144 |
| 推荐 | 4 个变体各 3 次，1 位评分员；再随机抽 25% 的回答加第二位评分员 | 144 | 180 | 324 |
| 稳妥 | 4 个变体各 5 次，2 位评分员 | 240 | 480 | 720 |

建议先跑“先看一眼”，看总分和区间；v25 对 none 的差都不明显，就不用往下跑。

## 评分的防线

- **引用核验。** 评分员判“有”必须引用回答里的原句；`score.py` 去回答里找，找不到的“有”改判为“无”，并在报告里统计数量。
- **盲评。** 评分提示词里没有变体名、没有 soul 条号。
- **自动字数项。** 简洁不靠评分员主观判。
- **评分员一致性。** 有两位评分员评过的回答，会算他们判断一致的比例。低于 85%，要么检查点写得不够客观，要么要多评几次。
- **先校准评分员（建议做一次）。** 自己写一份故意很差的回答和一份很好的回答，各评一遍，确认前者分很低、后者分很高，再大规模跑。

## 已知局限

- **同一个模型家族。** 被测者和评分员很可能是同一类模型，评分员可能偏爱自己的写法，也可能和被测者有共同盲点。分差大才可信；差几个百分点，当噪声。
- **模拟场景。** 全部是单轮文字：没有真工具，没有真文件，没有多轮来回。“真试过”“先看真东西”只能看回答里有没有按要求做的话和证据，看不出它真做了没有。
- **测的是回答质量，不是真实长任务。** 条号 13、18、20、21、22 没覆盖；多步任务里会不会跑偏、会不会忘记准则，这里测不到。
- **盲评有噪声。** 同一个回答，不同评分员可能判得不一样，所以要重复，要看区间和一致性，不要看单次。
- **检查点是按 v25 写的。** 有些检查点会偏向 v25 的措辞（例如“极限版”）。v16 没有这些条目，在这些点上吃亏是预期之内的，看“相对 none 的差”比看 v25 对 v16 更公平。
- **场景数量少。** 12 个场景，区间会很宽；单个条号只有 1 到 9 个检查点，不要对单条规则下结论。
- **v25+skill 的细则里有指向 SKILL.md 其他章节的引用**（“见核心原则”“见独当一面”），摘出来以后这些引用悬空。要完整版看 `v25+fullskill`。
- **场景是我们自己写的。** 陷阱来自我们对“不成熟 AI 会犯什么错”的想象；场景变了，结论可能变。后来加场景时，先写 rubric，再写场景，别看着某个版本的回答去调检查点。

## 加新场景

1. 在 `scenarios/` 写场景，文件内容只放发给 AI 的任务。
2. 在 `rubric/` 写同名文件：头部 `scenario`、`max_chars`、`traps`，然后每行一个检查点，格式 `- **C1** (第 N 条) 写明怎样算有`。每个检查点只挂一条规则，4 到 6 个。
3. `python3 build.py list` 确认能读出来。

## 第 4 轮说明

- 场景 15 的评分标准在第 4 轮前重写：C1/C2 改成 Ask-F1 式标准（默认受众 + 点明唯一决定，或只问一个带默认的问题），C5 改为“不假装已执行”，不再与 C3 重叠；场景文本未改。**第 3 轮的 15 号数字与第 4 轮不可比。**旧标准留在 `rubric-round3/15-该问没问.md`，`score.py --rubric-dir rubric-round3` 优先用该目录里的同名标准、没有的回退到 `rubric/`，所以第三轮的 89% / 78% 仍可复现。
- 新增场景 16（说明和代码冲突）、17（禁止类说明不能被代码覆盖，对照），变体 v28 = v26 + 第 5 条追加一句。
